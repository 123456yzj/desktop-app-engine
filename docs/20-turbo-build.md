# 多仓库构建工具

`vben-package` 是 Windows 构建工作台，复用引擎的 0.2 描述、布局、事件和日志。源界面模板位于 `examples/vben-package.json`，通过 `app.host: "vben-package"` 声明原生宿主；原生控制器位于 `src/bin/vben-package/turbo_build/`。统一引擎命令将 JSON 与宿主模板组合成单个可交付 EXE，保留扫描、分支切换和构建行为；开发时可使用 `--app` 调试模板。

工作台通过通用样式字段指定浅色背景、白色仓库面板、深色日志面板、蓝色主按钮、项目色标与分组连接栏。Grid 的 fr 高度将左右面板撑满剩余窗口空间。

会话日志预览显示扫描进度和仓库分支，扫描与分支列表的结构化 JSON 保留在原始 stdout 文件中，避免大段数据占满面板。构建进程的 stdout/stderr 仍可实时查看。

```powershell
cargo run --bin vben-package --locked --offline -- --check
cargo run --bin vben-package --locked --offline
```

先构建制作端引擎和宿主模板，再通过统一原生命令导出（后一条在 `cmd.exe` 中执行）：

```powershell
cargo build --release --bin desktop-app-engine --bin vben-package --locked --offline
```

```cmd
target\release\desktop-app-engine.exe package --output exports\vben-package.exe < examples\vben-package.json
```

制作端的宿主模板与引擎放在同一目录；客户只需导出的 `vben-package.exe`。统一接口见 [分发决策](06-packaging-decision.md)。

初始连接取自模板的 `state.sshTarget` 与 `state.repository`；当前用户保存的连接优先，保存在 `%LOCALAPPDATA%\DesktopAppEngine\apps\<EXE名>\connection.dat`，不回写应用定义。连接无效时打开设置；已有合法配置会自动扫描。认证由本机 OpenSSH 管理，不随包复制密钥。`--check` 仅校验定义；`--inspect` 无窗口执行只读扫描，输出数组包含根仓库（`id: "@root"`，存在时）及业务仓库。

扫描只列出 `apps` 一级目录中带独立 `.git` 和 `package.json` 的业务仓库，读取各自当前分支与提交。按目录名去掉 `web-` 前缀推导脚本名，再检查 Turbo 根目录 `package.json` 中真实存在的脚本。缺脚本或处于 detached HEAD 的仓库不可选择构建。

Turbo 根目录有独立 Git 仓库时，顶部连接栏依次显示 SSH 服务器、Turbo 工作区路径、根仓库分支与 Fetch/Pull；扫描状态位于页面标题右侧。业务面板标题右侧放置重新扫描和批量构建，下一行放搜索及选择数量、全选、清空和失败重试，操作集中在列表上方。根仓库目录符号链接按真实路径识别，操作在根仓库中执行。根仓库参与三个扫描入口的自动 Fetch，并复用相同的分支缓存、10 行下拉和立即 checkout 行为；不计入业务项目数量、全选或单项目打包。根目录没有独立 Git 仓库时，显示不可操作提示，仍可构建业务项目。

根仓库切换分支或 Pull 成功后，自动执行一次只读扫描，重新读取业务仓库和根目录构建脚本；Fetch 发现根仓库分支或 HEAD 被外部修改时，也会重新扫描。扫描完成前禁止构建，扫描失败后要求重新扫描，防止使用旧脚本状态。

启动应用且连接配置有效、成功保存连接设置、点击“重新扫描”这三个时机，都会扫描项目并逐个执行各仓库的 `git fetch --all --prune`，合并本地与远端分支并更新内存缓存。某个仓库刷新失败会保留其旧缓存，并继续刷新其他仓库；界面和日志显示失败信息。仓库行的 Fetch 可单独刷新该仓库。展开分支下拉框只显示缓存，不发起网络请求；尚未成功获取时提示点击 Fetch。列表最多同时显示 10 项，更多分支通过滚动查看。更换连接会清空旧工作区缓存；重启后通过启动扫描重新获取。

每行只有一个“分支”下拉框，默认显示仓库实际当前分支。选择其他有效分支后立即执行该仓库的 `git checkout`，无需额外按钮；选择当前分支不重复执行。切换期间显示所选分支及操作中状态，并锁定重复操作。结束后重新读取实际分支与提交；失败时恢复显示实际分支并显示错误，无法确认时显示“分支未确认”。Pull 执行普通 `git pull`。CLI 的 `--inspect` 保持只读仓库扫描，不执行 Fetch。

部分项目使用实际存在的 `build:dev:<业务>` 脚本，按扫描顺序串行执行。全部项目选中时使用一条 `pnpm build:dev`。确认页同时列出根仓库与业务仓库分支。确认后先校验根仓库（存在时）及整批业务仓库的分支、提交和脚本，再清理一次根目录 `.turbo`，每个构建进程启动前再次校验。根仓库 detached HEAD 时禁止构建。失败停止后续进程并标记未执行；重试建立新批次，包含失败及未执行项目，采用当前界面已读取的仓库状态，远端状态变化会要求重新扫描。

构建期间锁定连接、扫描、选择、分支和构建操作。右侧仍可切换批次或进程、复制预览、清空显示及打开日志目录。选中的进程不会被后续进程抢走。全选构建中各项目链接同一个共享进程。每条流保留 32 KiB 内存预览，面板合并后最多显示最近 48 KiB；完整原始输出写入磁盘。清空显示只移动当前预览起点，重新选择日志来源可恢复预览。

日志正文和日志元信息关闭溢出文本 tooltip。勾选“自动滚动”时跟随日志末尾；用户通过滚轮或滚动条改变日志位置后，自动取消勾选并暂停跟随，后续输出和界面刷新保留手动位置。再次点击“自动滚动”返回末尾并恢复跟随。

服务器需 Bash、Node.js、Git、pnpm，以及可供免交互 SSH 加载的环境。本机需 OpenSSH 客户端。扫描并刷新全部仓库分支超时 600 秒，单次只读扫描或仓库操作超时 120 秒，单个构建进程超时 3600 秒。关闭应用会取消本机 SSH 进程，服务器端命令是否退出由 SSH 和远端进程行为决定。

使用 `cargo run --bin vben-package --locked --offline -- --check` 校验业务模板及初始生成界面。构建计划、工作区状态约束、界面交互、连接设置以及真实 SSH、Bash、Git 与 pnpm 的集成行为需在目标环境验证。
